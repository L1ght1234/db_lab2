# Лабораторна робота №2: NoSQL та порівняння з PostgreSQL

Продовження проєкту **«Система управління спортивними подіями»** з використанням гібридної архітектури (**Polyglot Persistence**): **PostgreSQL 16 + MongoDB 7 + Redis 7**.

---

## 1. Види NoSQL баз даних

| Тип NoSQL | Модель зберігання | Типові представники | Для яких задач підходить |
|---|---|---|---|
| **Документні (Document)** | Колекції документів у форматі BSON/JSON із вкладеними об'єктами та масивами | MongoDB, Couchbase | Картки товарів/подій, каталоги з різними атрибутами, протоколи матчів, профілі |
| **Ключ-значення (Key-Value)** | Асоціативний масив (`key -> value`), часто in-memory з підтримкою TTL | Redis, Memcached, DynamoDB | Кешування, тимчасові блокування (бронь місць), сесії, лічильники, рейтинги |
| **Сімейства стовпців (Wide-Column)** | Рядки з динамічним набором колонок, оптимізовані під запис і діапазони | Apache Cassandra, ScyllaDB, HBase | Часові ряди (IoT, телеметрія), логування великих потоків подій |
| **Графові (Graph)** | Вузли (вершини), ребра (зв'язки) та їх властивості | Neo4j, Amazon Neptune | Соціальні мережі, рекомендації, пошук маршрутів та аналіз зв'язків |

## 2. Аналіз предметної області: що варто винести в NoSQL і чому

### Що залишається в PostgreSQL (реляційне ядро)
- `users`, `roles`, `sports`, `venues`, `teams`, `tournaments`, `tickets`, фінансові контракти спонсорів.
- **Аргументи:** тут критичні строгі транзакції (**ACID**), цілісність зовнішніх ключів і унікальні обмеження (наприклад, неможливість продати одне місце у квитку двічі при паралельних покупках).

### Що виноситься в MongoDB (документна БД, п.3–п.5)
Предметну область розширено функціоналом **детального live-матч-центру та спортивної статистики** (`match_protocols`).

**Аргументи на користь MongoDB для цього фрагмента:**
1. **Усунення багаторівневих `JOIN`-ів під час пікових читань:**
   У нормалізованому SQL один повний протокол матчу розбивається на **6 таблиць** (`matches`, `match_results`, `match_periods`, `match_period_stats`, `match_lineups`, `match_events`) плюс довідники (`sports`, `tournaments`, `venues`, `teams`, `players`). Під час популярного матчу тисячі глядачів одночасно відкривають його сторінку — у MongoDB весь протокол зберігається одним документом і читається за 1 звернення за індексом `matchId`.
2. **Поліморфна схема для різних видів спорту:**
   У системі є футбол, баскетбол, теніс. У кожного виду спорту своя структура періодів і метрик (у футболі — 2 тайми, володіння м'ячем, `xG`; у баскетболі — 4 чверті, триочкові, підбирання; у тенісі — 3 сети, ейси, подвійні помилки). У SQL доводиться використовувати EAV-таблиці (`match_period_stats(stat_key, stat_value)`) або зайві `NULL`-колонки, тоді як у MongoDB ці метрики природно лежать у вкладених об'єктах документа.
3. **Атомарний запис потоку подій:**
   Додавання нової події під час матчу (`$push` у `events` + `$inc` рахунку) оновлює один документ, не створюючи блокувань на суміжних транзакційних таблицях квитків.

### Коли NoSQL гірша за SQL (компроміси)
Денормалізація ускладнює оновлення довідників (наприклад, перейменування команди чи гравця вимагає `updateMany` по тисячах історичних документів) та наскрізну аналітику по окремому гравцю (потрібен `$unwind` великих документів замість швидкого пошуку у вузькій таблиці `match_lineups`). Саме ці кейси також перевіряються у бенчмарку!

## 3. Відображення NoSQL у SQL-таблиці (п.4–п.5)

Один документ колекції `match_protocols` у MongoDB відповідає **6 зв'язаним нормалізованим таблицям (3НФ)** у PostgreSQL (`sql/01_schema.sql`):

1. `matches` — метадані матчу, турніру, арени та команд.
2. `match_results` (1:1) — підсумковий рахунок і переможець.
3. `match_periods` (1:N) — тайми / чверті / сети з рахунком періоду.
4. `match_period_stats` (1:N до `match_periods`) — поліморфні показники команд за період (`stat_key`, `stat_value`).
5. `match_lineups` (1:N) — склади команд та індивідуальна статистика гравців.
6. `match_events` (1:N) — хронологія подій матчу.

## 4. Методика тестування швидкодії (`src/benchmark.ts`)

Щоб порівняння було об'єктивним:
- **Великий обсяг даних (`src/seed.ts`):** за замовчуванням генерується **20 000 матчів** різних видів спорту (майже **1 млн рядків** сумарно в SQL-таблицях та 20 000 документів у MongoDB).
- **Чесні індекси в обох БД:** усі реляційні ключі та фільтри проіндексовані в PostgreSQL (`sql/02_indexes.sql` + `ANALYZE`) і в MongoDB (включно з multikey-індексами на `lineups.playerId` та `events.playerId`). Плани виконання перевіряються через `EXPLAIN ANALYZE` та `explain('executionStats')`.
- **Один мережевий запит для читання в SQL:** картка матчу в PostgreSQL збирається за **1 запит** через `json_agg`, а не серією окремих запитів.
- **Прогрів (warm-up) та перцентилі:** заміряються `avg` і `p95`, а також конкурентне навантаження у **20 паралельних потоків**.
- **5 різнопланових сценаріїв:**
  1. Послідовне читання повного протоколу матчу за `matchId` (300x).
  2. Паралельне читання протоколу (1000x у 20 потоків, req/sec).
  3. Запис нового повного протоколу (транзакція з 6 таблиць у SQL vs `insertOne` у MongoDB, 100x).
  4. Аналітична агрегація статистики гравця за всі сезони (100x).
  5. Перейменування команди у всій історії (`UPDATE teams` в 1 рядку vs `updateMany` у денормалізованій MongoDB, 20x).

### Результати замірів (20 000 матчів, ~992 000 рядків у SQL-таблицях протоколу)

| Тест                                         | PG avg (мс) | PG p95 (мс) | Mongo avg (мс) | Mongo p95 (мс) | Порівняння                            |
|----------------------------------------------|------------:|------------:|---------------:|---------------:|---------------------------------------|
| 1. Читання протоколу матчу (300x послідовно) |        3.61 |        4.15 |           0.67 |           0.78 | Mongo швидше в 5.4x                   |
| 2. Конкурентне читання (1000x, 20 потоків)   |       11.60 |       20.69 |           4.82 |           7.99 | PG: 1712 req/s vs Mongo: 4126 req/s   |
| 3. Запис повного протоколу (100x)            |        6.14 |        6.63 |           0.70 |           0.86 | Mongo швидше в 8.8x                   |
| 4. Агрегація статистики гравця (100x)        |        1.57 |        3.59 |           2.41 |           6.94 | PG швидше в 1.5x                      |
| 5. Перейменування команди в історії (20x)    |        1.26 |        1.73 |          21.67 |          95.12 | PG швидше в 17.2x                     |

**Висновок із бенчмарку:**
- **Читання та запис цілого протоколу (тести 1–3):** MongoDB швидша в **5.4x** на читанні та в **8.8x** на записі (і дає **4126 req/s** проти **1712 req/s** під навантаженням), оскільки читає/записує 1 документ замість `JOIN` або транзакційної вставки одразу в 6 нормалізованих таблиць.
- **Агрегація по гравцю та оновлення довідників (тести 4–5):** PostgreSQL виграє в **1.5x** на вузькій аналітичній вибірці по `match_lineups` (без `$unwind` великих документів) і в **17.2x** на перейменуванні команди (`UPDATE` 1 рядка в `teams` проти масового `updateMany` по денормалізованих документах).

## 5. Другий тип NoSQL — Redis (`src/redisDemo.ts`, п.6)

Для задач реального часу використано **Key-Value / In-Memory базу Redis** (інший тип NoSQL відносно MongoDB):
- **String + TTL + NX (`SET key val EX 600 NX`):** тимчасове бронювання місця на стадіоні на 10 хвилин перед оплатою квитка (запобігає подвійному бронюванню без засмічення основної БД).
- **Hash (`HSET`, `HINCRBY`, `HGETALL`):** миттєве live-табло матчу в оперативній пам'яті.
- **Sorted Set (`ZADD`, `ZINCRBY`, `ZREVRANGE`, `ZREVRANK`):** живий рейтинг найкращих бомбардирів турніру за $O(\log N)$.
- **Cache-Aside (`GET` / `SETEX`):** кешування результату SQL-агрегації з PostgreSQL із TTL 30 секунд.

## Запуск

> У PowerShell за потреби використовуйте `npm.cmd` замість `npm`.

```bash
docker compose up -d

npm install

# 3. Згенерувати та залити 20 000 матчів (~1 млн рядків у SQL + 20k документів у MongoDB) + індекси
npm run seed

# 4. Демонстрація роботи з MongoDB (п.3)
npm run mongo

# 5. Бенчмарк швидкодії PostgreSQL vs MongoDB (п.5)
npm run bench

# 6. Демонстрація базових запитів у Redis (п.6)
npm run redis
```
